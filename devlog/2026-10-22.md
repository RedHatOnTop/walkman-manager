## Google's platform-tools on request (PR #5)

Yesterday's gap: Ubuntu's fastboot cannot make the userdata image `-w` writes. Bundling
adb and fastboot was ruled out (the Android SDK licence does not let anyone pass them on);
the app downloads Google's platform-tools instead, after the owner agrees to that licence,
the way the kit downloads the build-tools.

- The pin: platform-tools r37.0.1 for Linux, as `repository2-3.xml` lists it, 9,054,187
  bytes, sha1 `477254aa…` as the manifest says, sha256 `d230f138…`. It holds adb, fastboot,
  `mke2fs` with its `mke2fs.conf`, `make_f2fs` and `lib64/libc++.so`; fastboot asks for
  glibc 2.16 at most. It unpacks to `<data>/platform-tools`; its `source.properties` names
  the revision.
- What makes the image: fastboot runs the `mke2fs` beside its own binary with
  `-t ext4 -b 4096 -E android_sparse -O uninit_bg`, `MKE2FS_CONFIG` beside it too. The
  ZX507's userdata is ext4 (walkman-zx507's device report). The same arguments on this
  computer, into a 1024-block image:
  - e2fsprogs 1.47.3 `mke2fs`: exit 1, "Unimplemented ext2 library function while setting
    up superblock", as Debian's did yesterday;
  - Fedora's android-tools 37.0.0 `mke2fs.android`: exit 0, the image starts `3a ff 26 ed`
    (the sparse magic);
  - platform-tools 37.0.1 `mke2fs`: exit 0, the same magic.
- So the install plan has a `fastboot` gate. The app makes that image with the formatter
  beside the fastboot it will run, links followed, and reads the header: an update needs a
  fastboot that writes, a clean install or going back one that formats too. Closed, the gate
  offers the download. The fastboot is the downloaded one when there is one, else the one
  beside adb, else `PATH`'s; adb is `PATH`'s first and the downloaded one where there is
  none, and the device scanner takes it up as soon as it lands.
- Ubuntu's `/usr/bin/fastboot` is a link to `/usr/lib/android-sdk/platform-tools/fastboot`,
  and fastboot looks beside the path the link leads to; the first check looked beside the
  link. Both give "writes only" on Ubuntu; the check follows links now (unit test, not rerun
  on the VM).
- Packages: the rpm requires no tool package any more and recommends android-tools; the deb
  requires only `android-sdk-platform-tools-common` (its udev rule) and recommends adb and
  fastboot.

Run on fresh VMs (`scripts/dev/vm.sh`), each package from burst:

- Ubuntu 24.04, the deb with its recommends (30 s): Settings showed `/usr/bin/adb` and
  `/usr/bin/fastboot`, "writes only; can't format userdata". From Settings: the licence text
  came from Google, the agreement went to `licences.json` (`android-sdk-license`, sha256
  `de5fa465…`), the download landed in about a second, and Settings then showed the
  downloaded fastboot, "formats userdata too", adb still `/usr/bin/adb`.
- Fedora 44, the rpm without weak dependencies (49 s): no adb or fastboot. The first page
  said so and offered the download; after it the notice was gone, an adb server ran from the
  downloaded adb (`adb -L tcp:5037 fork-server server`), and Settings showed both tools from
  the download, fastboot formatting.
- Not run: the gate on the install page against a player (the VMs have none; the browser
  preview shows it closing, the download, and the gate opening on a fresh plan), and `-w`
  through the downloaded fastboot on the unit, which waits for the next wipe session.

From the PR's review: both containers build with Rust 1.99.1 from `rust-toolchain.toml`
(they had taken `stable`, which was 1.99.1); Node stays at the 22 line with the packages
locked by `package-lock.json`. `vm.sh` refuses a taken port at once and takes

the app has read with an SD card in. As the shell user it has no busybox, and SELinux keeps
`/proc/asound` from it. Two of the app's readings came out wrong.

- The clean install's microSD gate said the card was out while `sm list-volumes` had it
  mounted. toybox df lists the card only as `/dev/fuse` on `/storage/<id>`, since the shell
  user cannot stat `/mnt/media_rw/<id>`. The busybox fixture (a debug build) had only the
  second path. `/storage/<id>` (not `emulated` or `self`) is now a card too, its filesystem
  read from the vold mount behind it. The gate turned to "설치하는 동안 카드를 빼 두세요", and the

  denied`). `dumpsys media.audio_flinger` still answers the shell user. Where asound cannot be
  read, the probe takes each output thread's name, type, standby, sample rate, HAL format and
  channels. W.music played a track through an OFFLOAD thread at 44.1 kHz/16-bit (the at-rest
  threads are two 192 kHz/32-bit mixers), and the panel and the player render showed it.
  W.music was paused and the screen put back to sleep afterwards.
- Korean wrapped between syllables everywhere in the app ("필/요한"). `body` has `keep-all` now.

## The NW-A50 kit in the Studio, and its install page (feature/a50-android)

The owner asked for the A55's install to be offered step by step in this app, as the ZX507's
is. nw-a55 now has a kit (`kit/make-install.sh`, 24 steps) that turns the owner's backup, the
ford zip and the Fire OS update into what goes onto the player's WALKMAN drive plus the
picker UPG, described by an `install.json` of its own kind: a storage set.

Studio (d92a538):

- `wmBackup`: the vault keeps a `WMBACKUP` folder by its `manifest.txt` and md5-checks every
  image the manifest lists (`Damage::Unlike` names the one that differs). The owner's
  10-10 backup: 28 images, checked in about 7 s.
- A kit says `set = "storage"` and `variants = false`; the host check covers Python modules.
  The build reads `install.json` as a `StorageSet` and refuses one whose paths leave the
  drive, whose UPG is not last and at the root, or that keeps a file it does not copy.
- Run in the app, release binary `adb25ae7…` on a private Xvfb with a private data folder and
  `KIT_PREBUILT` pointing at the prebuilt release's files: build 2026-10-22-154109, 24 steps
  in 15 s. Against the hand run of the same kit (`install2`): `manifest.tsv`, the UPG, the
  data image, `container.tgz`, the modules and the picker are the same bytes;
  `android-boot.sh` and the MANIFEST differ because the hand run predates nw-a55 d0b2199;
  `fire-system.img` differs by debugfs times, which the kit keeps so PackageManager rescans.
- Found in that run: `install.json` said `commit: null` (the kit runs from a `git archive`
  copy, where `rev-parse` finds nothing) and curl's progress meter filled the build log. nw-a55
  d4f0675 reads the stamped `kit/COMMIT`, as walkman-zx507 does, and downloads quietly; the pin
  moved there. The build's file list had broken every path at its hyphens; it puts each path
  on one line with the folders dimmed.

Install (59580c6, 95720e8):

- `flash::drive`: the drive is LUN 0 of a USB disk whose vendor reads SONY and model WALKMAN
  (lsblk, sizes as numbers or as the strings lsblk wrote before 2.33), mounted through udisks
  as the desktop would. Each file goes to `.<name>.part`, is flushed, renamed, and its folder
  flushed. The read-back unmounts and mounts again and hashes from the drive.
- `flash::upg`: Sony's update command is rockbox scsitool's `do_fw_upgrade`: `fc 00 04 'dbmn'
  00 <flags> 00 00 00`, read 0x80 bytes, flags 0x80 first and 0 after it (the A55 refused
  0x80 with ILLEGAL REQUEST, ASC 0x24, and took 0, by hand earlier). A vendor opcode needs
  CAP_SYS_RAWIO, so `pkexec <the app> --upg-trigger /dev/sdX` sends it; that copy opens only a
  whole `/dev/sd[a-z]+` block device that answers INQUIRY as SONY / WALKMAN, and exits. From
  an AppImage, pkexec runs `$APPIMAGE`.
- `flash::storage::plan`: copies in the kit's order (an update keeps `android-data.img` when
  the drive has one), the read-back, `boot-choice` set to 1 when the drive's says otherwise
  (the picker starts what it started last, and only Walkman brings the drive back), the
  trigger, the wait, the log. Gates: model, drive, room (the largest moment counts each
  file's temporary copy beside its old one), the drive's `WMBACKUP/manifest.txt` against the
  build's backup (another one there is a newer backup; none is the owner's to vouch for),
  pkexec, and for an update the data to keep. The word to type is `bootswitcher.sh`, the one
  system file the UPG changes, or `android-data.img` when a clean install replaces it.
- The job waits up to 90 s for the player to leave USB and 15 min for the drive to come back,
  then reads what the UPG appended to `PICKERUPG.log` since the trigger (the log keeps every
  run) and whether `NW_WM_FW.UPG` became `.done`.
- burst: fmt, clippy `-D warnings`, 132 + 2 tests, the new ones included (lsblk shapes, the
  temporary-name copy and its cancel, the log offset, the plans for a fresh drive, an update,
  a clean install over data, closed gates, the room sum, the helper's path check).
- The page: drive gates and texts of their own, the copies folded into one row with every
  path and size under it (the kept image says so), the trigger as the owner's turn, and the
  drive's USB screen, the updater and the kit's picker (drawn from bootpick's frames, its
  English as on the player) on the stage. Looked at in the browser preview: the plan fresh
  and as an update, the file list, a copy at 46 %, the wait, the end with the picker, and a
  failed log check.

Not run: anything against the unit. The A55 was off USB all afternoon: `android-boot.sh down`
