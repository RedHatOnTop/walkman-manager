## Looking albums up and writing the tags

- `library::lookup` asks MusicBrainz (release search, then the release with recordings,
  artist credits and genres; covers from the Cover Art Archive) and the iTunes Search API
  at once. The Korean iTunes store answers no searches through the API (0 results even
  for "IU"), so the US store is asked, or the Japanese one for kana; it finds Korean
  releases from Korean text, under their English names ("This Song - EP" for 2AM
  "이노래"). MusicBrainz has the Korean titles.
- A search that names the artist and finds little is made again without it: the Coyote
  Ugly soundtrack is credited to "Various Artists", not to LeAnn Rimes.
- Results are ranked by our own score (title 60, artist 30, track count 10, on character
  pairs so Hangul compares as well as Latin); below 20 they are dropped.
- Files are paired with release tracks by title, length and number, each pair above a
  bar, so a single filed under a compilation is not forced onto track 1.
- `library::tags` writes through lofty's split/merge, so frames outside the generic set
  stay: the SensMe `GEOB` (application/SMFMF), Melon's `PRIV` and `WXXX`. A file keeps
  ID3v2.3 unless it had 2.4. Text that was CP949 or Shift_JIS marked Latin-1 is written
  back as Unicode on every write, since lofty would otherwise turn it into permanent
  mojibake when it re-encodes the frame.
- Writes go into a copy beside the file, which is read back (same type, length, rate,
  channels) before it replaces the file.
- On a player (`library::retag`): md5sum on the player, pull into
  `<data>/backups/<model>/<time>/`, compare checksums, write the copy, push it to
  `/data/local/tmp`, `cat` it into the original (so the media store keeps the row and
  the playlists that point at it), md5sum again, and put the backup back if it differs.

### Found on real files

- Melon downloads carry a `COMM` whose language is three NUL bytes; lofty refuses to
  write it ("invalid frame language found: \x00\x00\x00 (expected 3 ascii
  characters)"), so both 2AM files failed on the first try and were left untouched.
  Such codes now become `XXX`, ID3's unknown language.
- Reading the written copy back by path failed ("failed to parse file"): the
  `.uwm-part` name hides the type, so it is now read as the original's type.
- archive.org answered 500 once for a cover and MusicBrainz 503 once for a search; both
  are retried.

## SensMe channels

Asked at 20:25 together with the lookup. Music Center for PC leaves an SMFMF block in each
file it analyses (ID3 `GEOB` application/smfmf, FLAC APPLICATION `SMFM`, MP4
`moov/meta/ID32`); the Walkman turns it into channels on its own.

- Reverse engineering (20:32–21:31, Sonnet agent, firmware `libMediaStoreService.so` from
  the user's own player, run under an ARM emulator): the file carries no channel ids.
  The player takes the nearest of 48 centroids by weighted L1 over the 16 STBF values for
  the time channel (Morning … Midnight), eight predicates over the features for the mood
  channels (Energetic … Extreme), and a fallback mood when none fires. Chorus is STSA
  word 0 in ms, BPM the GBPM float. Write-up in `docs/sensme.md`, tools in `scripts/re/`.
- Re-run here at 21:29 from the agent's tools: 600 random feature sets through the emulated firmware
  against the Python model, 0 mismatches. The three sample MP3s give the firmware's own
  channels (Moonlight [1,5], Bohemian Rhapsody [3,7], Happy Together [1]).
- The centroids are Sony's, so they are never shipped: `sensme::Table` finds them in the
  user's own firmware file (CLASS_TABLE pattern; centroids 0x1800 before it, STHF and the
  fallback checked at their offsets) or in the JSON copy the app keeps after an import.
  Without a table the board still lists tempo and chorus.
- `library::sensme` decodes in one pass like the firmware; the CLI reproduces all 3,000
  stored reference vectors (six raw blobs whose header ident was corrupted are rejected
  as raw input and match once wrapped in a GEOB).
